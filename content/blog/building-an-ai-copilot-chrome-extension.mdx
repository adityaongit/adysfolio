Sales reps spend somewhere between 20–30% of their day on CRM updates. That's not a complaint — it's a number that shows up in every sales productivity study, and it's been true for years.

The problem isn't Salesforce. Salesforce is fine. The problem is that the data reps need to enter lives in a different place: in their emails, in their Zoom recordings, in their Fireflies transcripts, in their calendar notes. The manual step is copying information from those sources into CRM fields, and that step is slow, error-prone, and — critically — automatable.

At BrowserStack, we built a Chrome extension that eliminates most of that gap. Here's how it works.

## The Architecture at a Glance

A Chrome extension has a few moving parts: a content script that runs in the context of the active page, a background service worker, and optionally a popup or side panel. For this project, the side panel was the right choice — it gives you persistent UI alongside Salesforce without the lifecycle limitations of a popup.

The data flow looks like this:

```
Gmail / Zoom / Fireflies / Calendar
         ↓
   Chrome Extension (Content Scripts)
         ↓
   Background Service Worker
         ↓
   LLM Layer (field extraction, stage suggestion)
         ↓
   Side Panel UI (review + apply changes)
```

The key design decision was to keep humans in the loop. The extension *suggests* — it doesn't auto-write. Reps review extracted fields before anything touches Salesforce. This isn't just a UX preference; it's the right call for any AI system touching production data.

## Reading the Right Context

The hardest part wasn't the LLM work — it was building reliable integrations with four different platforms that each expose data differently.

**Gmail** via the Gmail API gives you structured message data. Clean JSON, well-documented, predictable.

**Zoom** recordings require working with the Zoom API to pull meeting metadata and transcripts. The transcript format is clean but you need to handle speaker attribution carefully if you want to extract who said what.

**Fireflies.ai** is arguably the easiest — their API is designed for exactly this kind of consumption and returns structured transcript data with timestamps and speaker labels.

**Google Calendar** gives you meeting metadata, attendees, and any notes attached to the event.

Each integration feeds into a unified context layer that normalizes these sources into a single object before anything hits the LLM:

```typescript
interface DealContext {
  dealId: string;
  recentEmails: EmailSnippet[];
  meetingTranscripts: TranscriptSegment[];
  calendarEvents: CalendarEvent[];
  currentFieldValues: Record<string, string>;
}
```

Normalization before LLM processing is important. You don't want the model doing structural interpretation — you want it doing *semantic* interpretation on clean input.

## Extracting Fields from Transcripts

The field extraction prompt is where most of the work lives. Salesforce deals have a lot of fields — deal size, close date, next steps, contact role, pain points, competitor mentions. You want to extract these from unstructured transcript text without hallucinating values that weren't said.

The trick is being explicit about what the model should do when it doesn't find a value:

```typescript
const extractionPrompt = `
You are extracting CRM field values from a sales call transcript.
For each field listed below, extract the value if explicitly mentioned.
If a value is not clearly stated, return null — do not infer or guess.

Fields to extract:
- deal_value: numeric value in currency
- close_date: expected close date
- next_steps: agreed next actions
- competitor_mentioned: any competitor names discussed
- pain_points: customer problems mentioned

Transcript:
${transcript}

Return a JSON object. Use null for any field not found.
`;
```

<TypographyMark>Instructing the model to return null rather than guess is one of the most underrated prompt engineering techniques.</TypographyMark> Hallucinated CRM data is worse than missing data — a rep can fill in a blank, but they have to notice and correct a wrong value first.

## Pipeline Stage Suggestions

Stage transitions are a classification problem. Given the current stage and the content of recent interactions, the model suggests whether to advance, hold, or flag a deal.

This works better as a reasoning task than a pure classification task. Instead of asking "what stage should this be?", we ask the model to reason through the evidence:

```typescript
const stagePrompt = `
Current stage: ${currentStage}
Recent activity summary: ${activitySummary}

Based on the evidence above, evaluate:
1. What buying signals are present?
2. What blockers or concerns were raised?
3. Given standard B2B sales progression, is this deal ready to advance?

Conclude with a recommendation: ADVANCE, HOLD, or FLAG, with a one-sentence reason.
`;
```

Forcing the model to reason step-by-step before concluding reduces confident-but-wrong outputs. The chain-of-thought pattern is genuinely useful here, not just a prompt engineering trick.

## The Salesforce Side

One thing that surprised me: you don't need the Salesforce API to read data from Salesforce when you have a Chrome extension. The content script runs in the page context and can observe the DOM directly.

This matters because getting Salesforce API credentials set up for enterprise accounts is a procurement and IT process that can take weeks. Reading from the DOM is immediate, and for most field values — current stage, deal name, open activities — the DOM has what you need.

Writing back to Salesforce, however, we do through the API. DOM manipulation to submit forms is fragile and breaks with every Salesforce UI update. API writes are reliable.

## What I'd Do Differently

The biggest thing I underestimated was Salesforce's DOM stability. Their Lightning Experience renders a lot of content dynamically, and selectors that worked last week stopped working after a routine Salesforce update. <TypographyMark>If you're building on top of a third-party web app's DOM, budget time for ongoing maintenance — it's not a one-time cost.</TypographyMark>

I'd also invest earlier in an evaluation layer. We ended up building one, but retrofitting evaluation onto a shipping feature is harder than building it in from the start. Track extraction accuracy against known-good examples before you deploy, not after.

The model is the easy part. The integrations, the data normalization, the edge cases — that's where the work actually lives.
